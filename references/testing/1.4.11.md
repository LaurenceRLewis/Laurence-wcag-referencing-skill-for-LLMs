# SC 1.4.11 Non-text Contrast (Level AA) — Manual Test Pattern

## 1 Overview

**SC:** 1.4.11 — Non-text Contrast (Level AA)
**Intent:** Verify that the visual boundaries, states, and meaningful graphical elements of UI components have at least 3:1 contrast against adjacent colours, so that low-vision users can perceive and operate the interface without relying on assistive technology.
**Scope of this test:** All interactive UI components (their boundaries and state indicators) and all informational graphical objects on the page.

---

## 2 Scope: what to test

Apply these tests to:

- Form field boundaries: text inputs, textareas, select menus, checkboxes, radio buttons, range sliders
- Button and link outlines where the boundary defines the component (borderless buttons relying on background alone may be exempt — see Step 3)
- Focus indicators: the visible focus ring or outline on any interactive element
- Component state indicators: the checkmark inside a checkbox, the filled circle inside a selected radio button, toggle switch tracks and thumbs, the indicator on a selected tab
- Informational icons: icons that convey meaning without adjacent text (e.g. a warning icon, a search icon used alone as a button)
- Data visualisation elements: chart lines, bars, data points, and segment boundaries where the graphical element conveys information

Do **not** test:

- Disabled or inactive components (explicitly exempt from SC 1.4.11)
- Purely decorative graphics and icons that have an equivalent text label immediately adjacent
- Logotypes and brand graphics
- Text and images of text (covered by SC 1.4.3)
- Components where the background alone (colour fill) distinguishes the component and the boundary is not the primary visual indicator — assess these under SC 1.4.1 instead

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Chrome, Edge, or Firefox) | Inspect computed CSS colours (`border-color`, `background-color`, `outline-color`, `color`) and element states | Yes |
| TPGi Colour Contrast Analyser (CCA) desktop app | Sample colours from the screen using the eyedropper and calculate contrast ratios | Yes |
| axe DevTools browser extension (or your preferred automation testing tool) | Automated scan to surface potential non-text contrast violations | Yes (core) |
| NVDA + Chrome, Edge, or Firefox (Windows) | Confirm that focus indicators are announced and that state changes are visible during keyboard navigation | Yes |
| JAWS + Chrome, Edge, or Firefox (Windows) | Secondary screen reader confirmation of focus visibility during keyboard navigation | No |
| VoiceOver + Safari (macOS / iOS) | Confirm focus indicator visibility on Apple platforms | Yes (built-in) |

> **Configuration note:** The CCA eyedropper samples the rendered pixel colour. Zoom the browser to 200% before sampling thin borders (1px borders can be anti-aliased and difficult to sample accurately at 100%). Ensure the OS colour profile matches the display profile to avoid skewed readings. Disable forced-colour or high-contrast OS modes before testing, as these override author styles and will not reflect the authored contrast ratio.

## 4 Test steps

### Step 1 Run automated checks

**Action:** Activate axe DevTools browser extension (or your preferred automation testing tool) and run a full-page scan. Note every violation or incomplete result flagged under the `non-text-contrast` rule.

**Expected result:** Zero violations under `non-text-contrast`, or each flagged item is a known false positive (see Section 6). Incomplete results require manual follow-up in Steps 2 to 6.

**Fail signal:** Any `non-text-contrast` violation not subsequently confirmed as a false positive in manual steps.

---

### Step 2 Check form field boundaries

**Action:** For every form field on the page (text input, textarea, select, checkbox, radio button), do the following. Open the CCA eyedropper. Sample the border or outline colour of the field. Then sample the adjacent background colour (the colour immediately outside the boundary). Read the contrast ratio in CCA.

For checkboxes and radio buttons, also sample the colour of the unchecked state boundary against its background. A checkbox or radio button that uses background colour alone to indicate state (no visible border in the unchecked state) must be assessed against the adjacent page background.

**Expected result:** Every field boundary has a contrast ratio of 3:1 or greater against the adjacent background.

**Fail signal:** Any field boundary reads below 3:1. A common failure is a light grey border (`#ccc`) on a white background, which typically produces a ratio of approximately 1.6:1.

---

### Step 3 Check buttons

**Action:** Identify all button components on the page. For each button, determine how the boundary is visually defined. Three cases apply:

**Case A — Button with a visible border or outline:** Sample the border colour and the adjacent background using CCA. The contrast of the border against the adjacent background must be 3:1 or greater.

**Case B — Button defined by background colour alone (no border):** The button boundary is conveyed by the contrast of the button's background against the page background. Sample the button fill colour and the adjacent page background. The contrast must be 3:1 or greater.

**Case C — Button with visible text but no distinct boundary or contrasting background:** This scenario indicates a potential failure. If the button is perceivable only by its text label (no border, no contrasting background, no other visual boundary), it may fail 1.4.11. Assess whether any boundary characteristic meets 3:1.

**Expected result:** Every button has at least one boundary characteristic (border or background fill) that produces 3:1 or greater contrast against the adjacent surface.

**Fail signal:** No boundary characteristic meets 3:1. The button is indistinguishable from its surrounding surface without relying on the text label alone.

---

### Step 4 Check focus indicators

**Action:** Use keyboard Tab navigation to move focus through every interactive element on the page: links, buttons, inputs, custom controls. For each focused element, do the following. Open CCA. Sample the colour of the focus indicator (the outline, ring, underline, or highlight). Sample the colour of the surface immediately adjacent to the focus indicator (this may be the page background, or a component background). Read the contrast ratio.

Do not dismiss the focus ring before sampling. Use the keyboard to hold focus on the element while operating the CCA eyedropper.

**Expected result:** Every focus indicator produces at least 3:1 contrast against the adjacent surface.

**Fail signal:** Focus indicator colour contrast falls below 3:1. A thin `outline: 1px dotted #767676` on a white background (approximately 4.6:1) would pass; `outline: 1px dotted #ccc` on white (approximately 1.6:1) would fail.

> **Note:** SC 1.4.11 requires 3:1 for the focus indicator as a UI component boundary. SC 2.4.11 (Focus Not Obscured) and SC 2.4.13 (Focus Appearance, AAA) impose additional requirements beyond contrast ratio and are tested separately.

---

### Step 5 Check component state indicators

**Action:** For each stateful interactive component, test both the active/selected state and, where applicable, the intermediate state.

**Checkbox (checked state):** Activate a checkbox so it is checked. Sample the checkmark (tick) colour against the checkbox background fill. The contrast of the checkmark against its fill must be 3:1 or greater. If the checked state changes the border colour, also sample that against the adjacent page background.

**Radio button (selected state):** Select a radio button. Sample the filled inner circle against the radio button background.

**Toggle/switch:** Sample the toggle thumb against the track colour in both on and off states.

**Selected tab or step indicator:** Sample the active indicator (underline, filled background, or marker) against its adjacent background.

**Expected result:** Every state indicator within a component meets 3:1 against the surface it is placed on.

**Fail signal:** A white checkmark on a pale blue checked background falling below 3:1; a light grey radio button inner circle on a white background; a toggle thumb that merges visually with the track.

---

### Step 6 Check informational icons and graphical objects

**Action:** Identify all icons that convey meaning without an immediately adjacent visible text label (e.g. a standalone search icon used as a button, a warning triangle in an error message, chart lines or data points). For each, sample the icon or graphical element colour against its adjacent background using CCA.

For charts, test each data series line, bar fill, or data point. If the graphical element is bounded by a stroke, the stroke colour (not the fill) must meet 3:1 against the adjacent background.

**Expected result:** Every informational icon and graphical element meets 3:1 against its background.

**Fail signal:** A light blue chart line on a white chart background; a pale warning icon on a white card; a data point whose colour merges with the chart background.

---

### Step 7 Verify states under browser zoom

**Action:** Set browser zoom to 200%. Repeat the CCA sampling from Steps 2 to 6 for at least one representative component of each type (one input, one button, one focused element, one icon). At 200%, borders and focus rings may render differently due to scaling.

**Expected result:** All sampled contrast ratios remain at 3:1 or greater at 200% zoom.

**Fail signal:** A 1px border that appeared to pass at 100% now anti-aliases to a colour that samples below 3:1 at 200% zoom. Record and report the specific combination and zoom level.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated scan | Zero `non-text-contrast` violations, or all flagged items confirmed false positives | Any unresolved violation or incomplete result not cleared by manual testing |
| 2 Form field boundaries | Every field border is 3:1 or greater against adjacent background | Any field border falls below 3:1 (e.g. light grey on white) |
| 3 Buttons | Button boundary (border or background fill) is 3:1 or greater against adjacent surface | No boundary characteristic meets 3:1; button not perceivable from its surroundings |
| 4 Focus indicators | Focus indicator colour is 3:1 or greater against adjacent surface on every interactive element | Focus indicator falls below 3:1 on any element |
| 5 Component state indicators | State indicator (checkmark, fill, thumb, marker) is 3:1 against the surface it sits on | State indicator merges visually with its background below 3:1 |
| 6 Informational icons and graphics | Icon or graphical element is 3:1 against adjacent background | Any informational icon or chart element falls below 3:1 |
| 7 Zoom verification | Contrast ratios hold at 3:1 or greater at 200% zoom | Anti-aliasing or scaling causes a previously passing element to fall below 3:1 at zoom |

**Overall result:** The page **passes** SC 1.4.11 only when every applicable step passes.
A single step failure = **SC 1.4.11 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **Disabled form fields:** An input with `disabled` or `aria-disabled="true"` is explicitly exempt from SC 1.4.11. A greyed-out disabled field with low-contrast borders does not constitute a failure.
- **Decorative icons with adjacent text:** A decorative chevron icon inside a button that already has a visible text label ("Next") is not required to meet 3:1, because the icon is decorative relative to the labelled control. Only icons that convey information independently must meet the requirement.
- **Background-colour-only buttons assessed incorrectly:** If the button boundary is defined by background fill, the contrast must be measured between the button fill and the page background, not between the text and the button fill (that is covered by SC 1.4.3).
- **Hover state only:** If a focus indicator only becomes visible on hover, assess the hover state. However, if the component has no keyboard focus indicator at all, this is a failure of SC 2.4.7, not 1.4.11.

These situations can look like passes but are not:

- **Relying on text contrast to infer component visibility:** If a button's text meets 4.5:1 but the button has no visible boundary (no border, no background contrast), the button boundary itself may still fail 1.4.11. Text contrast (SC 1.4.3) and non-text contrast (SC 1.4.11) are separate requirements.
- **Sampling the wrong adjacent colour:** On a card component with a white background inside a grey page, the input border must be measured against the card background (white), not the page background (grey). Always sample the immediately adjacent surface.
- **CSS `outline: none` with a custom focus style:** A custom focus style (e.g. a box shadow or background change) still must meet 3:1 contrast. `outline: none` alone without a qualifying replacement is a failure of SC 2.4.7 and may also be a failure of 1.4.11 if no alternative indicator is present.

---

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 1.4.1 Use of Colour (Level A):** Components that rely on colour alone to convey state (e.g. a red border as the only error indicator, with no icon or text) may fail both 1.4.1 and 1.4.11 if the border contrast is also insufficient.
- **SC 1.4.3 Contrast Minimum (Level AA):** Text within form fields and buttons is assessed under 1.4.3. Non-text contrast covers the field border and button boundary; text contrast covers the input text and label.
- **SC 2.4.7 Focus Visible (Level AA):** If focus indicators are absent entirely, 2.4.7 fails. If present but low-contrast, 1.4.11 fails. Both must be tested together during keyboard navigation.
- **SC 2.4.11 Focus Not Obscured Minimum (Level AA, new in WCAG 2.2):** Covers whether the focused component is hidden by overlapping content. Distinct from contrast, but tested at the same time during keyboard navigation.
- **SC 2.4.13 Focus Appearance (Level AAA):** Defines minimum area and contrast requirements for focus indicators (stricter than 1.4.11 alone). Not required for standard AA conformance, but useful to check for best practice.
