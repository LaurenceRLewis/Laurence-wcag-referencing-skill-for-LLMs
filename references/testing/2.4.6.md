# SC 2.4.6 Headings and Labels (Level AA) — Manual Test Pattern

## 1 Overview

**SC:** 2.4.6 Headings and Labels (Level AA)
**Intent:** Verify that headings and labels, where present, are descriptive enough to communicate the topic or purpose of the content or input they introduce.
**Scope of this test:** All headings (`<h1>`–`<h6>` and elements with `role="heading"`) and all form labels (`<label>`, `aria-label`, `aria-labelledby`) present in the page.

---

## 2 Scope: what to test

Apply these tests to:

- Page and section headings: `<h1>` through `<h6>`, and any element with `role="heading"`
- Form field labels: `<label>` elements, `aria-label` values, and `aria-labelledby` references
- Fieldset legends: `<legend>` elements grouping related form controls
- Table captions and column/row headers: `<caption>`, `<th>` elements used as labels

Do **not** test:

- Whether headings or labels are present at all (that is SC 1.3.1 for structure and SC 3.3.2 for form labels — not this SC)
- Heading hierarchy or nesting order (covered by SC 1.3.1)
- Whether labels are programmatically associated with their controls (covered by SC 1.3.1 and SC 4.1.2)
- Decorative or presentational headings that carry no structural meaning

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Chrome, Edge, or Firefox — Elements panel) | Inspect heading elements, label text, and ARIA label attributes | Yes |
| A11y Quick Check browser extension | Run "Identify text marked up as a heading", "Verify large bold text is not a heading", and "Show form control attributes" checks | Yes |
| axe DevTools browser extension (or your preferred automation testing tool) | Automated scan to flag empty or generic heading/label patterns | Yes (core) |
| NVDA + Chrome, Edge, or Firefox (Windows) | Navigate by heading and form mode to hear how headings and labels are announced | Yes |
| JAWS + Chrome, Edge, or Firefox (Windows) | Verify heading and label announcements with a commercial screen reader | No |
| VoiceOver + Safari (macOS / iOS) | Verify heading and label announcements on Apple platforms | Yes (built-in) |

> **Configuration note:** For heading navigation in NVDA, press `H` to jump between headings in Browse Mode. In JAWS, press `H` in Virtual PC Cursor mode. In VoiceOver on macOS, use `VO+Command+H`. For form navigation in NVDA and JAWS, press `F` to move between form fields and listen to the label announced for each control. In VoiceOver, use `VO+Command+J`.

---

## 4 Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 Run automated and visual checks

**Action:** Activate A11y Quick Check and run the following checks from the "Content and Structure" tab: "Identify text marked up as a heading" and "Verify large bold text is not a heading". Then run "Show form control attributes" from the "Usability and Readability" tab. Review the overlay annotations. Then activate axe DevTools browser extension (or your preferred automation testing tool) and run a full-page scan. Note any violations related to: `empty-heading`, `label`, `aria-label`, or similar heading and label rules.

**Expected result:** Zero violations in heading and label categories, or each flagged item is confirmed as a false positive in Step 2.

**Fail signal:** Any unflagged-as-false-positive violation in heading or label content rules.

---

### Step 2 Review all headings for descriptiveness

**Action:** Open DevTools. Use the Elements panel to locate all heading elements (`<h1>`–`<h6>`) on the page, or run the following in the Console to list them: `document.querySelectorAll('h1, h2, h3, h4, h5, h6, [role="heading"]')`. Read the text content of each heading. Ask: does this heading describe the content that follows it? Could a user reading only the headings understand the page structure and find the section they need?

**Expected result:** Every heading clearly describes its section. A user scanning headings alone can identify what each section contains without needing to read the body content.

**Fail signal:**
- Headings are generic: "Section 1", "Part A", "Overview", "More Information", "Content" with no further context.
- Headings are identical across multiple sections with no differentiating text.
- Headings contain placeholder text such as "Heading" or "Title Here".
- Headings are used for visual styling only (e.g., a heading that reads "———" or uses an icon character) and convey no topic.

---

### Step 3 Review all form labels for descriptiveness

**Action:** Locate all form controls on the page. For each, identify its label source: a `<label>` element, `aria-label` attribute, `aria-labelledby` reference, or `<legend>` within a `<fieldset>`. Read the label text. Ask: does this label tell the user what information to enter, or what the control does?

**Expected result:** Every label clearly identifies the purpose of the associated input. Examples of descriptive labels: "Email address", "Date of birth (DD/MM/YYYY)", "Confirm new password", "Country of residence".

**Fail signal:**
- Labels are generic or non-descriptive: "Field 1", "Input", "Enter here", "Name" (when multiple name fields exist without differentiation such as "First name" and "Last name").
- `aria-label` values are technical strings: class names, IDs, or developer notes such as `aria-label="input-2"` or `aria-label="TODO"`.
- A `<legend>` describes a fieldset only as "Options" or "Details" with no indication of what kind of options or details.

---

### Step 4 Check labels on controls with shared or ambiguous context

**Action:** Identify any group of similar controls that share a visual context established by surrounding content but rely on that context for their label to be meaningful, such as a table of radio buttons where the column heading provides the question. For each, check that the accessible name of each individual control is descriptive on its own, or that the group label (via `<fieldset>`/`<legend>` or `role="group"` with `aria-labelledby`) provides the necessary context programmatically.

**Expected result:** Each control either has a fully self-describing label, or is part of a labelled group where the group label plus the individual label together form a complete, descriptive name.

**Fail signal:**
- A standalone radio button is labelled only "Yes" or "No" with no group label that provides the question being answered.
- A table cell contains a checkbox with no label, relying solely on visual column and row position to convey meaning.

---

### Step 5 Verify headings and labels via screen reader navigation

**Action:** Navigate the page in two passes using at least two of the following combinations: NVDA + Chrome, Edge, or Firefox; JAWS + Chrome, Edge, or Firefox; VoiceOver + Safari.

Pass 1 (headings): Use the screen reader's heading navigation key (`H` in NVDA or JAWS Virtual PC Cursor mode; `VO+Command+H` in VoiceOver). Listen to every heading announced. Note the heading level and text.

Pass 2 (form labels): Activate the screen reader's forms navigation (`F` in NVDA or JAWS; `VO+Command+J` for form controls in VoiceOver). Tab through every form control and listen to the label announced before or alongside the control.

**Expected result:**
- Every heading announcement makes sense out of context and describes a distinct section.
- Every form control announcement includes a label that clearly identifies the input's purpose.

**Fail signal:**
- Screen reader announces headings that are generic or identical ("Section, heading level 2" repeated four times with no differentiating text).
- Screen reader announces a form field with no label, a placeholder only, or a label that is a technical string.
- A control is announced with only its type and no name: "Edit, blank" or "Checkbox" with no associated label text.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated and visual checks | Zero relevant violations, or all flagged items confirmed false positives | Any heading or label content violation not resolved |
| 2 Heading descriptiveness | Every heading clearly describes the section it introduces; headings scanned in isolation convey page structure | Any heading is generic, placeholder, purely decorative, or identical to another with no differentiating text |
| 3 Form label descriptiveness | Every form control label clearly identifies the input's purpose | Any label is generic, a technical string, or ambiguous without surrounding visual context |
| 4 Shared-context labels | Controls in groups have a programmatically associated group label that provides the necessary context | Controls rely solely on visual layout or surrounding text with no programmatic group label |
| 5 Screen reader navigation | All headings and labels announced by the screen reader are descriptive and unambiguous | Any heading or label sounds generic, missing, or meaningless when heard in screen reader navigation |

**Overall result:** The page **passes** SC 2.4.6 only when every applicable step passes.
A single step failure = **SC 2.4.6 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **Short but descriptive headings:** A heading like "Summary" or "Contact" is acceptable if it accurately describes the section content and is not repeated identically across multiple sections. Brevity is not a failure.
- **Placeholder text in design prototypes:** If testing a live production page, ignore prototype or CMS default text that was never intended to be published. Confirm with the team whether the content is live before recording a failure.
- **Labels that appear generic but have group context:** A radio button labelled "Yes" inside a `<fieldset>` with `<legend>Receive marketing emails?</legend>` is descriptive in context. The group label provides the topic; the individual label provides the choice. This passes.
- **Technical field names that are industry-standard:** Labels like "IBAN", "BIC/SWIFT", "NI number", or "VAT registration number" are specific and descriptive for their audience. They are not generic even if they are abbreviations.

These situations can look like passes but are not:

- **A visible heading that is replaced by `aria-label`:** If a heading element has `aria-label="Section overview"` but the visible text reads "Part 3", the accessible name is descriptive but the visual label is not. Both the visible and programmatic label should be descriptive. The visible label is what sighted users rely on; a mismatch between the two is a failure.
- **Labels that describe the input type, not the purpose:** "Text field", "Dropdown", or "Date picker" tell the user what kind of control it is, not what information to enter. These fail SC 2.4.6 even though they are non-empty labels.
- **Headings that describe layout, not content:** "Left column", "Main area", "Top section" are structural descriptions, not content descriptions. They are non-descriptive and fail this SC.

---

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 1.3.1 Info and Relationships (Level A):** If headings are present but non-descriptive, there is often also a failure to mark up content structure programmatically. Missing `<label>` associations are a 1.3.1 failure; this SC addresses whether those labels, once present, are descriptive.
- **SC 2.4.4 Link Purpose in Context (Level A):** Pages with generic headings often also contain generic link text ("Read more", "Click here") where the heading would otherwise provide the required context. A failure in 2.4.6 can therefore cause a cascading failure in 2.4.4.
- **SC 2.4.10 Section Headings (Level AAA):** Requires section headings to be used to organise content. A page that uses headings but makes them non-descriptive may simultaneously fail 2.4.10, depending on the conformance target.
- **SC 3.3.2 Labels or Instructions (Level A):** Requires that labels or instructions are provided for user input. This SC does not duplicate 3.3.2, but a label that exists and passes 3.3.2 (present and associated) may still fail 2.4.6 if its text is non-descriptive.
- **SC 4.1.2 Name, Role, Value (Level AA):** If a label is non-descriptive because the `aria-label` value is a technical string or placeholder, this is simultaneously a 4.1.2 failure (the accessible name does not describe the control's purpose).
