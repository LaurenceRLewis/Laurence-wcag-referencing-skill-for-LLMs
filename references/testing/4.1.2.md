# SC 4.1.2 Name, Role, Value (Level A) — Manual Test Pattern

## 1 Overview

**SC:** 4.1.2 Name, Role, Value (Level A)
**Intent:** Verify that every UI component exposes a correct accessible name, a correct role, and correct programmatic state to assistive technologies, and that state changes are reflected in real time.
**Scope of this test:** All interactive UI components: buttons, links, form controls, custom widgets, and any element with `tabindex` or an ARIA role.

---

## 2 Scope: what to test

Apply these tests to:

- Buttons (native `<button>` and elements styled as buttons)
- Links (`<a>` with `href`)
- Form inputs: text, checkbox, radio, select, textarea
- Icon-only controls (no visible text label)
- Custom widgets: accordions, tabs, modals/dialogs, comboboxes, sliders, date pickers
- Toggle controls: expand/collapse triggers, toggle buttons, switches
- Any element with `role=`, `aria-label`, `aria-labelledby`, or `aria-describedby`
- Dynamic components where state changes on user interaction

Do **not** test:

- Static text, headings, paragraphs, and non-interactive images (covered by SC 1.1.1 and SC 1.3.1)
- Purely decorative elements marked with `aria-hidden="true"` or `alt=""`
- Content outside the page's main viewport that is never reachable by keyboard

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Elements / Accessibility panel) | Inspect the accessibility tree, ARIA attributes, and computed accessible name | Yes |
| axe DevTools browser extension (or Deque axe) | Automated scan to surface missing names and incorrect roles before manual testing | Yes (core) |
| NVDA + Firefox (Windows) | Screen reader verification of announced name, role, and state | Yes |
| VoiceOver + Safari (macOS / iOS) | Screen reader verification on Apple platforms | Yes (built-in) |
| Accessibility Insights for Web (browser extension) | Tab stops overlay and accessible name / role inspector | Yes |

> **Configuration note:** Before testing with a screen reader, disable browser auto-fill and notifications. Set NVDA to "Say all" mode off; use arrow/Tab navigation. For VoiceOver, use VO+Shift+Down to enter a web area, then Tab or VO+Right to navigate elements.

---

## 4 Test steps

### Step 1 Run an automated scan

**Action:** Install and activate axe DevTools (or Accessibility Insights FastPass). Run a full-page scan. Export or note every violation flagged under rules related to: `button-name`, `link-name`, `label`, `aria-required-attr`, `aria-valid-attr-value`, `aria-roles`.

**Expected result:** Zero violations in the categories above, or each violation is confirmed as a false positive in Step 2.

**Fail signal:** Any unflagged-as-false-positive violation in the name, label, role, or ARIA attribute categories.

---

### Step 2 Inspect accessible names in the accessibility tree

**Action:** Open DevTools. In Chrome/Edge: Elements panel → Accessibility tab → select each interactive element in turn. In Firefox: Inspector → Accessibility panel. For each element, read the "Name" and "Role" fields in the panel.

**Expected result:**
- Every interactive element has a non-empty computed Name.
- The Name is meaningful (describes the element's purpose, not just "button" or "icon").
- The Role matches the element's function (e.g., `button`, `checkbox`, `dialog`, `tab`).

**Fail signal:**
- Name is empty, null, or equals a generic string such as the element's tag name.
- Role is `generic` or `none` on an element that is interactive.
- `aria-labelledby` references an ID that does not exist in the DOM (check the Console for ARIA warnings).

---

### Step 3 Check icon-only and image-based controls

**Action:** Identify all controls that have no visible text — icon buttons, image buttons, social share buttons, close (×) buttons, hamburger menus. For each: inspect the element in DevTools and check for `aria-label`, `aria-labelledby`, or `<title>` inside an inline SVG. Also check that the icon element itself carries `aria-hidden="true"` or `focusable="false"`.

**Expected result:**
- Each icon-only control has a non-empty `aria-label` (or equivalent) that describes its action (e.g., `aria-label="Close dialog"`).
- The icon (`<svg>`, `<img>`, or icon font `<span>`) is hidden from the accessibility tree via `aria-hidden="true"`, so the name is not duplicated.

**Fail signal:**
- Icon-only button has no text alternative; computed Name in DevTools is empty.
- `aria-label` exists but its value is a filename, class name, or symbol (e.g., `aria-label="icon-close"`).
- The SVG `<title>` is present but the `<svg>` has `aria-hidden="true"`, negating the title.

---

### Step 4 Verify ARIA roles on custom widgets

**Action:** Identify all components built from non-semantic elements (`<div>`, `<span>`) that behave interactively. For each, inspect the element's `role` attribute in DevTools. Cross-reference with the ARIA Authoring Practices Guide pattern for that widget type (modal → `role="dialog"`, tab → `role="tab"`, etc.).

**Expected result:**
- Every custom interactive component carries the correct ARIA `role`.
- Required owned or owning relationships are present (e.g., `role="tablist"` contains elements with `role="tab"`; `role="dialog"` has `aria-modal="true"` and `aria-labelledby` pointing to its heading).
- No native element carries a redundant explicit role that matches its implicit role (e.g., `<button role="button">` is incorrect markup but not a testable failure; flag as a code quality issue).

**Fail signal:**
- A custom modal is a `<div>` without `role="dialog"` and `aria-modal="true"`.
- A custom combobox is missing `role="combobox"` and the associated `role="listbox"` on the dropdown.
- A custom tab strip has no `role="tablist"` container.

---

### Step 5 Test state changes interactively (keyboard + DevTools)

**Action:** For each stateful control (expand/collapse trigger, checkbox, toggle button, menu button, accordion header, tab), do the following:
1. Focus the element with Tab.
2. Activate it (Enter or Space).
3. Immediately inspect the element in the DevTools Accessibility panel and read the current state properties.
4. Activate it again to reverse the state and re-inspect.

Key states to verify:

| Control type | Attribute to check | Expected values |
|---|---|---|
| Expand / collapse trigger | `aria-expanded` | `"false"` → `"true"` → `"false"` |
| Checkbox | `aria-checked` (custom) or `checked` (native) | `"false"` ↔ `"true"` |
| Toggle button | `aria-pressed` | `"false"` ↔ `"true"` |
| Tab | `aria-selected` | `"false"` ↔ `"true"` |
| Menu button | `aria-expanded` | `"false"` → `"true"` on open |
| Disabled control | `aria-disabled` or `disabled` | Remains `"true"` |
| Invalid input | `aria-invalid` | `"true"` when validation fails |

**Expected result:** The ARIA state attribute updates in the DOM synchronously when the control's visual state changes. The DevTools panel reflects the new state without a page reload.

**Fail signal:**
- The visual state changes (e.g., accordion opens) but the `aria-expanded` attribute remains unchanged.
- The attribute updates in the DOM but is set to a non-boolean string (e.g., `aria-expanded="open"` instead of `"true"`).
- State is conveyed only via CSS class (e.g., `.is-open`) with no corresponding ARIA attribute.

---

### Step 6 Screen reader verification (name, role, state)

**Action:** Navigate the page using a screen reader (NVDA + Firefox recommended; VoiceOver + Safari as an alternative). Use Tab to move through interactive elements. For each element, listen to the full announcement. Record what is spoken for: name, role, state.

For form inputs: additionally navigate with the screen reader's Forms Mode / Quick Nav off (NVDA: `Insert+Space` to toggle; VoiceOver: use Tab, not VO+Arrow).

**Expected result:**
- Screen reader announces: **[name] [role] [state]** in that order (exact wording varies by screen reader).
  - Example (button): *"Close dialog, button"*
  - Example (checkbox, unchecked): *"Subscribe to newsletter, checkbox, not checked"*
  - Example (accordion, collapsed): *"Billing details, button, collapsed"*
- State changes are announced immediately after activation without requiring the user to re-navigate to the element.

**Fail signal:**
- Screen reader announces only the role with no name, or announces a file path, CSS class, or icon glyph as the name.
- Screen reader announces stale state after activation (e.g., still says "collapsed" after the accordion has opened).
- Screen reader skips the element entirely (may indicate `aria-hidden="true"` on a focusable element — a separate but related failure).

---

### Step 7 Check for `aria-hidden` applied to focusable elements

**Action:** Search the page's HTML (DevTools Elements panel or "Find in page" with `aria-hidden`) for all instances of `aria-hidden="true"`. For each, check whether the element or any of its descendants has a `tabindex` value ≥ 0, or is a natively focusable element (`<a href>`, `<button>`, `<input>`, `<select>`, `<textarea>`).

**Expected result:** No element marked `aria-hidden="true"` is reachable by keyboard focus. Decorative SVG icons and presentation images are hidden correctly. Focusable elements inside hidden containers are also suppressed using `display:none`, `visibility:hidden`, `inert`, or `tabindex="-1"`.

**Fail signal:**
- A `<button>` or `<input>` inside an `aria-hidden="true"` container is still reachable by Tab — the element is invisible to AT but operable by keyboard, creating a "ghost" control.
- An entire interactive section is hidden from AT while remaining visually and keyboard-accessible.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated scan | Zero relevant violations, or all flagged items confirmed false positives | Any name, label, role, or ARIA attribute violation not resolved |
| 2 Accessibility tree names | Every interactive element has a non-empty, meaningful computed Name and correct Role | Name is empty, null, or a generic/meaningless string; Role is incorrect or absent |
| 3 Icon-only controls | Every icon control has a meaningful `aria-label`; icon is hidden from AT | No text alternative present; label is a filename or symbol |
| 4 Custom widget roles | All custom widgets carry correct ARIA roles with required relationships | Widget built on `<div>`/`<span>` without appropriate `role`; required parent/child roles missing |
| 5 State changes (DOM) | ARIA state attributes update synchronously with visual state changes | Attribute unchanged after interaction; incorrect value format used |
| 6 Screen reader announcement | Name, role, and state all announced correctly; state changes announced in real time | Missing name, incorrect state, stale state after interaction |
| 7 `aria-hidden` on focusable elements | No focusable element is inside an `aria-hidden="true"` container | Keyboard-reachable element is hidden from AT |

**Overall result:** The page **passes** SC 4.1.2 only when every applicable step passes.
A single step failure = **SC 4.1.2 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **`role="presentation"` on a layout table:** A `<table>` used purely for layout with `role="presentation"` (or `role="none"`) is intentionally stripping the semantic role. This is correct use of ARIA, not a failure, provided no data relationships rely on the table structure.
- **Empty `alt` on a decorative image inside a link:** If a link contains both a decorative `<img alt="">` and visible text, the image correctly has an empty alt. The link name comes from the visible text. This is a pass.
- **`aria-hidden` on an SVG icon inside a labelled button:** The button has `aria-label="Submit"` and the SVG inside has `aria-hidden="true"`. This is correct, the icon is decorative; the name comes from `aria-label`. Not a failure.
- **Placeholder text as the only "label":** A visually apparent input might look labelled due to placeholder text, but `placeholder` is not a substitute for a programmatic label. This **is** a failure (Step 2), not a false positive.

These situations can look like passes but are not:

- **`title` attribute as the sole name:** Many browsers expose `title` as the accessible name fallback, and some screen readers announce it. However, `title` is not reliably announced across all AT and relies on mouse hover to be visible. An input with only a `title` and no `<label>` is a failure.
- **`aria-label` present but with a meaningless value:** DevTools will show a non-empty Name, but if the value is `"icon"`, `"div"`, or a technical string, it does not meet the intent of SC 4.1.2. Record as a failure in Step 2.
- **State announced by screen reader but not in the DOM:** Some browser/screen reader combinations infer state from CSS or DOM position. Do not assume a pass because the screen reader announces it correctly in one combination — verify the state is programmatically set in the DOM (Step 5).

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 1.3.1 Info and Relationships (Level A):** Structure and relationships conveyed visually must also be programmatically determinable. A missing `role` on a custom widget may simultaneously fail 1.3.1.
- **SC 2.1.1 Keyboard (Level A):** Custom widgets without correct roles often also lack correct keyboard interaction patterns.
- **SC 2.5.3 Label in Name (Level A):** When a control has a visible text label, the accessible name must contain that text. A mismatch between visible label and `aria-label` value can satisfy 4.1.2 (name exists) but fail 2.5.3 (name doesn't match visible text).
- **SC 3.3.1 Error Identification (Level A):** `aria-invalid="true"` is part of 4.1.2's state requirement; the error message surfacing is tested under 3.3.1.
- **SC 4.1.3 Status Messages (Level AA):** Dynamic announcements that don't receive focus (e.g., live regions) are separately covered by 4.1.3, but missing `aria-live` is often discovered during 4.1.2 state testing.
