# SC 1.3.1 Info and Relationships (Level A) — Manual Test Pattern

## 1 Overview

**SC:** 1.3.1 Info and Relationships (Level A)
**Intent:** Verify that all information, structure, and relationships conveyed through visual presentation are also available programmatically, so assistive technologies can understand and convey them correctly.
**Scope of this test:** All content whose meaning depends on visual structure: headings, lists, tables, forms, groupings, required fields, and emphasis.

---

## 2 Scope: what to test

Apply these tests to:

- Headings and document structure (visual titles, section labels)
- Lists: bulleted, numbered, and definition-style
- Data tables (grids presenting relational information)
- Form inputs: labels, groupings, required fields, and error states
- Visual emphasis where meaning is intended (bold, italic)
- Any structural relationship conveyed by layout, colour, or typography alone

Do **not** test:

- Layout tables used purely for visual arrangement where `role="presentation"` or `role="none"` is correctly applied (covered by SC 4.1.2)
- Static decorative content with no structural meaning
- Purely visual styling where no meaning is conveyed (for example, a decorative horizontal rule)

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Elements panel) | Inspect HTML structure, element types, ARIA attributes, and computed accessibility tree | Yes |
| axe DevTools browser extension (or Accessibility Insights FastPass) | Automated scan to surface missing labels, incorrect roles, and structural violations | Yes (core) |
| NVDA + Firefox (Windows) | Screen reader verification that structure is announced correctly | Yes |
| VoiceOver + Safari (macOS / iOS) | Screen reader verification on Apple platforms | Yes (built-in) |

> **Configuration note:** In NVDA, use Heading Navigation (H key) to move between headings, List Navigation (L key) for lists, and Table Navigation (T key) for tables. In VoiceOver, use the Rotor (VO+U) to browse headings, form controls, and tables independently.

---

## 4 Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 Run an automated scan

**Action:** Install and activate axe DevTools (or Accessibility Insights FastPass). Run a full-page scan. Note every violation flagged under rules related to: `heading-order`, `label`, `table-duplicate-name`, `td-headers-attr`, `th-has-data-cells`, `region`, `list`, `listitem`, `definition-list`.

**Expected result:** Zero violations in the above categories, or each flagged item is confirmed as a false positive in subsequent steps.

**Fail signal:** Any unresolved violation in heading, label, table, list, or region categories.

---

### Step 2 Inspect heading structure

**Action:** Open DevTools Elements panel. Search the DOM for any element styled to look like a heading (large or bold text, section titles) that is not an `<h1>`–`<h6>` element. Also check that heading levels are used in a logical hierarchy (no skipping from `<h1>` to `<h4>`).

Alternatively, use the Accessibility Insights Headings visualisation, or in NVDA press H to navigate heading by heading and listen for announcements.

**Expected result:**
- All visual headings are marked up as `<h1>`–`<h6>`.
- Heading levels reflect document hierarchy without skipping levels arbitrarily.
- No `<div>`, `<p>`, or `<span>` elements styled to appear as headings unless they carry `role="heading"` and `aria-level`.

**Fail signal:**
- A visual section title is a `<div class="heading">` or similar with no semantic heading element or `role="heading"`.
- Heading levels skip (for example, `<h1>` followed immediately by `<h4>`) in a way that misrepresents structure.

---

### Step 3 Inspect list structure

**Action:** Locate all content presented visually as a list (bulleted, numbered, or definition-style). Inspect each in DevTools and confirm the HTML element type.

**Expected result:**
- Bulleted lists use `<ul>` containing `<li>` elements.
- Numbered/ordered lists use `<ol>` containing `<li>` elements.
- Definition or name/value pairs use `<dl>`, `<dt>`, `<dd>`.
- No list items exist outside a list container.

**Fail signal:**
- List items are a series of `<div>`, `<p>`, or `<span>` elements styled with bullets or numbers via CSS.
- `<li>` elements appear outside `<ul>` or `<ol>`.

---

### Step 4 Inspect data table structure

**Action:** Locate all tables on the page. For each, inspect the HTML in DevTools and check: that header cells use `<th>` (not `<td>`), that `<th>` elements have a `scope` attribute (`col`, `row`, `colgroup`, or `rowgroup`), and that complex tables use `id`/`headers` associations. Check for a `<caption>` where the table's purpose is not obvious from surrounding context.

**Expected result:**
- All data tables use `<th scope="...">` for header cells.
- Complex tables with multiple header levels use `id`/`headers` to associate cells correctly.
- A `<caption>` is present or the table's purpose is clear from an immediately preceding heading.

**Fail signal:**
- All cells are `<td>` with no `<th>` elements; header relationship is conveyed by position or bold text only.
- `scope` attribute is absent from `<th>` elements.
- A layout table presents data relationships and has not been marked with `role="presentation"`.

---

### Step 5 Inspect form labels and groupings

**Action:** For every form input on the page, inspect the HTML in DevTools and check:
1. Each `<input>`, `<select>`, and `<textarea>` has an associated `<label>` via `for`/`id` pairing, or is wrapped by a `<label>` element, or has `aria-label` or `aria-labelledby`.
2. Related inputs (radio buttons, checkboxes sharing a question) are grouped inside `<fieldset>` with a `<legend>`.
3. Required fields have `required` or `aria-required="true"` on the input element itself (not only a visual asterisk).

**Expected result:**
- Every input has a programmatically associated label.
- Radio/checkbox groups are wrapped in `<fieldset>`/`<legend>`.
- Required fields carry `required` or `aria-required="true"`.

**Fail signal:**
- An input's only label is placeholder text (`placeholder` attribute) with no `<label>` element or ARIA equivalent.
- Radio buttons sharing a visual question have no `<fieldset>`/`<legend>` grouping.
- Required fields are marked with a visual asterisk or colour only, with no programmatic indicator on the element.

---

### Step 6 Inspect emphasis and semantic meaning

**Action:** Locate any text that is visually bold or italic where the intent is to convey meaning (for example, a warning, a key term, or stress emphasis). Inspect the element in DevTools.

**Expected result:**
- Meaningful bold text uses `<strong>`.
- Meaningful italic text uses `<em>`.
- Purely decorative bold or italic styling (for visual style only) uses `<b>` or `<i>`, or applies CSS directly, and does not mislead AT.

**Fail signal:**
- Text conveying importance or stress uses `<b>` or `<i>` where `<strong>` or `<em>` is semantically correct.
- CSS `font-weight: bold` applied to a `<span>` or `<div>` where the bold conveys meaning that a screen reader user would miss.

---

### Step 7 Screen reader verification of structure

**Action:** Navigate the page with NVDA + Firefox (or VoiceOver + Safari). Perform each of the following:

1. Use heading navigation (H key in NVDA; Rotor in VoiceOver) to move through headings. Listen for the heading level announced.
2. Use list navigation (L key in NVDA) to locate lists. Listen for the list and item count announced.
3. Navigate into a data table (T key in NVDA). Arrow through cells and listen for header associations announced per cell.
4. Tab through form fields. For each, listen for the announced label and, where applicable, the "required" state.

**Expected result:**
- Headings are announced with their correct level: "Heading level 2, Contact details."
- Lists are announced as lists with item counts: "List of 4 items."
- Table cells are announced with their associated header: "Region, North."
- Form fields are announced with their label and required state: "Email address, edit, required."

**Fail signal:**
- A visual heading is announced as plain text with no heading level.
- A visual list is read as a sequence of text with no list announcement.
- Table cells are announced without header context.
- A required form field has no "required" announcement.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated scan | Zero relevant violations, or all flagged items confirmed false positives | Any unresolved heading, label, table, or list violation |
| 2 Headings | All visual headings are semantic `<h1>`–`<h6>` with logical hierarchy | Visual heading uses `<div>`/`<p>`; heading levels skip arbitrarily |
| 3 Lists | All visual lists use `<ul>`, `<ol>`, or `<dl>` with correct child elements | List items created with unsemantic elements styled via CSS |
| 4 Data tables | All header cells use `<th scope="...">` with correct associations | No `<th>` or `scope`; data relationships conveyed by visual position only |
| 5 Form labels and groupings | Every input is labelled programmatically; groups use `<fieldset>`/`<legend>`; required state is programmatic | Label is placeholder only; radio group has no `<fieldset>`; required is visual only |
| 6 Emphasis | Meaningful emphasis uses `<strong>` or `<em>` | Meaningful emphasis uses `<b>`, `<i>`, or CSS only |
| 7 Screen reader | Headings, lists, tables, and form fields all announced correctly with structure intact | Any structural element announced as plain text; required state or header context missing |

**Overall result:** The page **passes** SC 1.3.1 only when every applicable step passes.
A single step failure = **SC 1.3.1 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **`<b>` and `<i>` used for stylistic purposes:** When bold or italic is applied for visual style with no intended semantic meaning, `<b>` and `<i>` are correct HTML. They are only a failure when the visual styling is intended to convey importance or stress emphasis that a screen reader user would otherwise miss.
- **Layout table with `role="presentation"`:** A `<table>` used purely for layout that carries `role="presentation"` (or `role="none"`) is intentionally stripping table semantics. This is correct use of ARIA, provided the table contains no data relationships.
- **`aria-label` or `aria-labelledby` on a form input with no visible `<label>`:** An input labelled exclusively via ARIA has a programmatic label and passes SC 1.3.1. Note that this may still fail SC 2.5.3 (Label in Name) if the visible text does not match the ARIA label, and SC 3.3.2 (Labels or Instructions) if no visible label exists at all.
- **Headings that skip levels for presentational reasons when ARIA overrides are applied:** A `<h3>` styled as a subheading below an `<h1>` may look like a skip but be intentional if the page structure is flat. Evaluate hierarchy in context.

These situations can look like passes but are not:

- **Placeholder text as the only label:** An input with a visible, meaningful placeholder looks labelled, but `placeholder` is not a programmatic label. It disappears on input and is not reliably announced by all AT. This is a failure of SC 1.3.1 (and also SC 3.3.2).
- **Visual asterisk for required fields without a programmatic indicator:** A red asterisk next to a field label conveys required status visually. Without `required` or `aria-required="true"` on the input, screen reader users receive no indication. DevTools will show the asterisk in the label text but the input element itself will have no required property.
- **`<th>` present but missing `scope`:** The presence of `<th>` elements does not automatically pass the table test. Without `scope` attributes, associations between headers and data cells are ambiguous in complex tables, and AT may not announce them correctly.

---

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 4.1.2 Name, Role, Value (Level A):** Missing or incorrect roles on custom components often simultaneously fail 1.3.1. A custom heading widget without `role="heading"` and `aria-level` is an example.
- **SC 2.4.6 Headings and Labels (Level AA):** Requires headings and labels to be descriptive. A heading that is semantic (`<h2>`) but uninformative ("Section 1") passes 1.3.1 but may fail 2.4.6.
- **SC 3.3.2 Labels or Instructions (Level A):** Requires that labels or instructions are provided for user input. An input without any visible label fails both 1.3.1 (no programmatic label) and 3.3.2 (no visible instruction).
- **SC 2.5.3 Label in Name (Level A):** When a visible text label exists, the programmatic accessible name must contain it. A mismatch between visible label and `aria-label` value may pass 1.3.1 (a name exists) but fail 2.5.3.
- **SC 1.3.2 Meaningful Sequence (Level A):** Structural failures in 1.3.1 often accompany sequence failures where DOM order does not reflect visual reading order.
