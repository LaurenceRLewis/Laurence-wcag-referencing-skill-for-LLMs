# SC 1.4.4 Resize Text (Level AA) — Manual Test Pattern

## 1 Overview

**SC:** 1.4.4 Resize Text (Level AA)
**Intent:** Verify that all text on the page can be resized up to 200% using browser zoom without loss of content or functionality, and without requiring assistive technology.
**Scope of this test:** All text content on the page, including body copy, headings, labels, form field text, button text, tooltips, error messages, and dynamically inserted text.

---

## 2 Scope: what to test

Apply these tests to:

- Body text and paragraphs
- Headings at all levels
- Form labels, input text, placeholder text, and error messages
- Button and link text
- Navigation items and menu labels
- Tooltip and popover text
- Text in modal dialogs and overlays
- Dynamically inserted or updated text (notifications, validation messages, live regions)
- Text inside data tables (cell content, headers, captions)

Do **not** test:

- Captions for video content (governed by SC 1.2.2 and 1.2.4, not this SC)
- Images of text (covered separately by SC 1.4.5)
- Non-text UI components such as icons, borders, or decorative imagery (covered by SC 1.4.11)
- Horizontal scrolling behaviour at 320 CSS pixels viewport width (that is SC 1.4.10 Reflow, not this SC)

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Chrome, Edge, or Firefox) | Inspect CSS units for font sizes and identify fixed `px` declarations; verify computed font sizes at 200% zoom | Yes |
| A11y Quick Check browser extension | No dedicated resize check exists for this SC. Use during Step 5 to confirm visible text and control labels are present after zoom-triggered reflow. | Yes |
| axe DevTools browser extension (or your preferred automation testing tool) | Automated scan to flag known resize-related failures | Yes (core) |
| NVDA + Chrome, Edge, or Firefox (Windows) | Confirm text is readable and announced correctly at 200% browser zoom | Yes |
| JAWS + Chrome, Edge, or Firefox (Windows) | Confirm text is readable and announced correctly at 200% browser zoom | No |
| VoiceOver + Safari (macOS / iOS) | Confirm text is readable and announced correctly at 200% browser zoom | Yes (built-in) |

> **Configuration note:** Before testing, set the browser viewport to 1280px wide. Do not use DevTools responsive mode — it emulates a device and can affect how the page renders. Instead, open DevTools and resize the browser window (or the DevTools panel edge if docked to the right) while watching the dimension readout that appears in the top-right corner of the page. Drag until the readout shows 1280 for the width. This readout is visible in Chrome, Edge, and Firefox whenever DevTools is open and the window is being actively resized. If DevTools is docked to the right, opening or closing it will shift the viewport width. After docking, recheck the viewport width by running `window.innerWidth` in the DevTools Console and adjust the window edge until it returns 1280. This is a consistency convention, not a WCAG requirement, but it ensures results are reproducible across testers. Use the browser's built-in zoom control, not OS-level display scaling or assistive technology text enlargement. In Chrome and Edge, use Ctrl + (Windows/Linux) or Cmd + (macOS) to increase zoom. In Firefox, use the same keyboard shortcut or enable "Zoom Text Only" under View > Zoom for a stricter text-only resize test. Reset zoom to 100% between steps.

## 4 Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 Run automated and visual checks

**Action:** Activate axe DevTools browser extension (or your preferred automation testing tool) and run a full-page scan. Note any violations related to text resize or fixed font size rules. There are no dedicated text resize checks in A11y Quick Check for this SC; automated scanning is limited to axe DevTools for this step.

**Expected result:** Zero violations related to text resize, or each flagged item is confirmed as a false positive after manual review in subsequent steps.

**Fail signal:** Any unflagged-as-false-positive violation in text resize or font size categories.

---

### Step 2 Inspect CSS font size units

**Action:** Open DevTools. Navigate to the Elements panel and inspect a representative sample of text elements, including at least one heading, one body paragraph, one form label, one button, and one error message if present. For each, open the Computed styles panel and check the `font-size` value. Note whether the base font sizes in the stylesheet use fixed `px` values or relative units (`rem`, `em`, `%`). Run the following in the Console to list elements with a computed font size of 12px or below (a common indicator of fixed small text): `Array.from(document.querySelectorAll('*')).filter(el => parseFloat(getComputedStyle(el).fontSize) < 13 && el.innerText?.trim()).map(el => ({tag: el.tagName, text: el.innerText.trim().slice(0,40), size: getComputedStyle(el).fontSize}))`.

**Expected result:** Font sizes are set using relative units (`rem`, `em`, `%`) so that browser zoom scales them proportionally. No text is locked to a fixed `px` size that prevents zoom from affecting it.

**Fail signal:** Font sizes are declared in `px` in a way that prevents browser zoom from scaling them. Note that `px` units do respond to browser zoom in modern browsers; a fail here requires confirmation in Step 3 that scaling is actually broken.

---

### Step 3 Zoom to 200% and check for content loss

**Action:** Before zooming, confirm the browser viewport is 1280px wide. With DevTools open, slowly drag the browser window edge and watch the dimension readout in the top-right corner of the page until it shows 1280 for the width. Do not use DevTools responsive mode. If DevTools is docked to the right, run `window.innerWidth` in the Console after docking to recheck, as docking shifts the viewport width. Adjust the window edge until it returns 1280. Set browser zoom to 200% using Ctrl/Cmd +. Scroll through the entire page at this zoom level. For each content area, check: (a) is all text still visible and readable? (b) is any text clipped, truncated, or hidden by `overflow: hidden`? (c) does any text overlap other text or UI components to the point that it becomes unreadable? (d) are any controls (buttons, links, form fields) still operable and their labels still visible?

**Expected result:** All text content remains readable at 200% zoom. Text reflows or wraps rather than overflowing or being clipped. No content disappears. All interactive controls remain operable and labelled.

**Fail signal:**
- Text is clipped and not recoverable by scrolling (cut off by a container with `overflow: hidden`).
- Text overlaps adjacent text or UI elements to the point of becoming unreadable.
- Text disappears entirely (e.g., set to a fixed height container that does not grow).
- Button or link labels are truncated to the point that their purpose can no longer be determined.
- Form field labels are hidden when adjacent inputs expand, obscuring the label.

---

### Step 4 Test text-only zoom in Firefox

**Action:** Reset browser zoom to 100% and confirm the viewport is still 1280px wide. Drag the window edge while watching the dimension readout, or run `window.innerWidth` in the Console if DevTools is docked to the right, and adjust if needed. In Firefox, navigate to View > Zoom and enable "Zoom Text Only". Then use Ctrl/Cmd + to increase text zoom to 200%. Scroll through the page and repeat the checks from Step 3: look for clipped, truncated, overlapping, or disappeared text. This test isolates text scaling from layout scaling and catches failures that browser zoom alone may mask.

**Expected result:** Same as Step 3. Text scales visually and all content remains readable and functional when only text is zoomed.

**Fail signal:** Same fail conditions as Step 3. Additional failure: layout elements that depend on text height (e.g., fixed-height buttons, single-line truncated containers) break when only the text is enlarged, hiding content that was visible at full browser zoom.

---

### Step 5 Check dynamically inserted text at 200% zoom

**Action:** With browser zoom still at 200%, interact with any dynamic page features: submit an incomplete form to trigger validation error messages, trigger any tooltips or popovers, activate modal dialogs, and observe any live region updates (notifications, chat messages, status updates). Check that all dynamically inserted text is visible, readable, and not clipped.

**Expected result:** All dynamically inserted text appears at the zoomed scale and remains readable. Error messages, tooltips, and modal content all conform to the same standard as static content.

**Fail signal:** Error messages appear but are clipped or overflow their container at 200% zoom. Tooltip text is cut off. Modal dialog text overlaps or is hidden behind fixed-position UI elements.

---

### Step 6 Verify with screen reader at 200% zoom

**Action:** With browser zoom at 200%, navigate the page using at least one of the following combinations: NVDA + Chrome, Edge, or Firefox; JAWS + Chrome, Edge, or Firefox; VoiceOver + Safari. Tab through interactive elements and use heading navigation to move through the page. Confirm that the screen reader announces all text correctly, including any text that required scrolling or reflow to become visible.

**Expected result:** The screen reader announces all text content correctly at 200% zoom. No text that was visually present is absent from the accessibility tree. No truncated visible text results in a truncated announcement.

**Fail signal:** The screen reader announces text that is not visible on screen (clipped by CSS but still in the DOM), or fails to announce text that should be present. Truncated visual labels result in truncated accessible names being announced.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated and visual checks | Zero relevant violations, or all flagged items confirmed as false positives | Any resize-related violation is not resolved after manual review |
| 2 CSS font size units | Font sizes use relative units, or are confirmed via Step 3 to scale correctly with browser zoom | Font sizes are fixed in a way that prevents browser zoom from scaling them |
| 3 Zoom to 200% content check | All text is visible, readable, and unclipped at 200% browser zoom; all controls remain operable | Any text is clipped, truncated, overlapping, or hidden; any control label is unreadable |
| 4 Firefox text-only zoom | All text scales and remains readable when text-only zoom is applied to 200% | Any text is clipped, hidden, or overlaps adjacent content under text-only zoom |
| 5 Dynamic text at 200% zoom | All dynamically inserted text is visible and readable at 200% browser zoom | Any dynamic text (errors, tooltips, notifications) is clipped or hidden at 200% zoom |
| 6 Screen reader at 200% zoom | Screen reader announces all text accurately; no mismatch between visible and accessible content | Screen reader announces clipped or absent text, or fails to announce visible text |

**Overall result:** The page **passes** SC 1.4.4 only when every applicable step passes.
A single step failure = **SC 1.4.4 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **Horizontal scrollbar appears at 200% zoom:** The appearance of a horizontal scrollbar at 200% browser zoom is not a failure of SC 1.4.4. It may indicate a failure of SC 1.4.10 (Reflow), but this SC only requires that text is not lost or clipped, not that the layout is scroll-free.
- **Text wraps onto multiple lines:** Text wrapping to additional lines at 200% zoom is the correct behaviour and is not a failure. Reflow is expected and acceptable.
- **`px` units in CSS:** The presence of `px` units for font sizes does not automatically fail this SC. In modern browsers, `px` units do respond to browser zoom. A failure requires evidence that text is actually clipped or lost at 200% zoom, not merely that `px` is used.
- **Zoom triggers a mobile or responsive layout:** If the page responds to 200% zoom by switching to a mobile-responsive layout, this is acceptable provided all text content remains accessible and no content is lost in the transition.

These situations can look like passes but are not:

- **Text appears visible but is positioned off-screen:** Text that has been repositioned off-screen using `position: absolute` with large negative values, or `left: -9999px`, may appear absent visually but remain in the DOM. Confirm with DevTools that visible text is in the viewport, not merely present in the accessibility tree.
- **Container scrolls internally at 200% zoom:** A fixed-height scrollable container may appear to retain all its content because it is scrollable, but if the scroll affordance is not obvious or the container's scroll behaviour was unintended, this can still represent a loss of usability. Evaluate whether a typical user would discover the scroll at 200% zoom.
- **JavaScript re-renders text at a capped size:** Some implementations use JavaScript to detect zoom level and re-render text at a fixed visual size, effectively counteracting the user's zoom. This is a clear failure even if the text appears readable, because the user's intent to resize has been overridden.

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 1.4.10 Reflow (Level AA):** Requires that content can be presented without horizontal scrolling at a viewport width of 320 CSS pixels. Layouts that fail reflow often also clip or hide text at 200% zoom, making both SC relevant when text overflow issues are found.
- **SC 1.4.12 Text Spacing (Level AA):** Requires that no loss of content or functionality occurs when text spacing is overridden. Containers with fixed heights that clip text at 200% zoom will frequently also clip text when spacing is increased, making this SC a co-failure candidate.
- **SC 1.4.5 Images of Text (Level AA):** Text rendered as images does not scale with browser zoom in the same way as live text, and may appear blurred or pixelated at 200%. If images of text are found during this test, raise a potential SC 1.4.5 failure separately.
- **SC 1.4.3 Contrast Minimum (Level AA):** At high zoom levels, layout reflow can cause text to move onto backgrounds of different colours, potentially introducing contrast failures that were not present at 100% zoom. Note any new contrast concerns observed during Step 3.
- **SC 4.1.2 Name, Role, Value (Level AA):** If text truncation at 200% zoom causes button or form label text to be clipped, the accessible name derived from visible text (via `aria-labelledby` or implicit labelling) may also be affected, producing a co-failure in accessible naming.
