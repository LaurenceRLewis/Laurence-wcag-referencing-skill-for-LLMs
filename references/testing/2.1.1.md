# SC 2.1.1 Keyboard (Level A) — Manual Test Pattern

## 1 Overview

**SC:** 2.1.1 Keyboard (Level A)
**Intent:** Verify that all functionality can be reached and operated through a keyboard interface alone, without requiring specific timing for individual keystrokes, so users who cannot use a pointing device can complete every task.
**Scope of this test:** All interactive functionality on the page, including native controls, custom scripted widgets, hover-triggered behaviour, and drag-and-drop interactions.

---

## 2 Scope: what to test

Apply these tests to:

- All native interactive elements: links, buttons, form inputs, selects, textareas
- Custom scripted widgets built from `<div>`, `<span>`, or other non-interactive elements (menus, tabs, sliders, comboboxes, tree views, date pickers, carousels, accordions)
- Functionality exposed only on hover or mouseover (tooltips, flyout menus, reveal-on-hover controls)
- Drag-and-drop interactions, sortable lists, range sliders, and canvas or map controls
- Modal dialogs, drawers, and overlays
- Media players and any custom transport controls

Do **not** test:

- The visibility or appearance of the focus indicator (covered by SC 2.4.7 and SC 2.4.13)
- Whether the tab order is logical (covered by SC 2.4.3)
- Whether focus can be moved away again once inside a component (covered by SC 2.1.2 No Keyboard Trap)
- Path-dependent input where the path itself is essential, such as freehand drawing or handwriting recognition. These are exempt by the SC. Confirm the path is genuinely essential before excluding the function.
- Static, non-interactive content with no scripted behaviour

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Keyboard only (Tab, Shift+Tab, Enter, Space, Arrow keys, Escape, Home, End) | Manually reach and operate every control without a pointing device | N/A |
| Browser DevTools (Chrome, Edge, or Firefox, Elements panel) | Inspect element roles, `tabindex`, and event listeners to find non-semantic and mouse-only controls | Yes |
| A11y Quick Check browser extension | Run "Validate Tabindex usage" from the "Usability and Readability" tab to surface positive or misused `tabindex`, and to help locate non-semantic interactive elements | Yes |
| axe DevTools browser extension (or your preferred automation testing tool) | Automated scan to flag clickable elements without a keyboard-accessible role or interactive semantics | Yes (core) |
| NVDA + Chrome, Edge, or Firefox (Windows) | Verify keyboard operability when the screen reader is active, including Browse Mode and Focus Mode behaviour | Yes |
| JAWS + Chrome, Edge, or Firefox (Windows) | Verify keyboard operability with a commercial screen reader, including Virtual PC Cursor and Forms Mode | No |
| VoiceOver + Safari (macOS / iOS) | Verify keyboard and VoiceOver cursor operability on Apple platforms | Yes (built-in) |

> **Note:** Automated tools can flag elements that have a mouse handler but no keyboard support or interactive role. They cannot confirm that a widget actually behaves correctly from the keyboard. Operability of custom widgets is inherently manual. Unplug or set aside the mouse for the keyboard-only steps so you cannot fall back to it without noticing. In Firefox, if Tab does not reach all controls, set `about:config` → `accessibility.tabfocus` to `7`.

---

## 4 Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 Run automated and visual checks

**Action:** Activate A11y Quick Check and run "Validate Tabindex usage" from the "Usability and Readability" tab. Note any positive `tabindex` values and any non-semantic elements pulled into the tab order. Then activate axe DevTools browser extension (or your preferred automation testing tool) and run a full-page scan. Note any violations relating to interactive roles, clickable elements without keyboard support, or `tabindex`.

**Expected result:** Zero relevant violations, or each flagged item is confirmed as a false positive in a later step.

**Fail signal:** A clickable element is reported with no keyboard-accessible role or interactive semantics, indicating a control that a pointer can use but a keyboard cannot.

---

### Step 2 Inventory interactive elements and event handlers

**Action:** Build a list of everything that does something when clicked. Open DevTools → Elements → Event Listeners and inspect `click`, `mousedown`, `mouseup`, `mouseover`, and `mouseenter` handlers. For each element carrying a pointer handler, note its tag and role: a native `<button>`, `<a href>`, or input is keyboard-ready by default, while a `<div>`, `<span>`, `<i>`, or `<svg>` with a click handler is a candidate failure to confirm in later steps.

**Expected result:** A complete inventory of interactive elements, each classed as native (keyboard-ready) or custom (needs verification).

**Fail signal:** Not applicable at this step. This step is discovery only.

---

### Step 3 Reach every control with the keyboard

**Action:** Place focus at the top of the page (click the browser address bar, then press Tab to enter the document). Using only Tab and Shift+Tab, move through the page. For composite widgets that expose a single tab stop, also use the documented Arrow, Home, and End keys to reach inner items. Confirm that every element from the Step 2 inventory can be reached.

**Expected result:** Every interactive control can be reached by keyboard, either as a tab stop or as an inner item reachable with the expected Arrow or Home/End keys inside a focused composite widget.

**Fail signal:** A control that responds to a mouse cannot be reached by any keyboard means. A common cause is a `<div>` or `<span>` with a click handler and no `tabindex="0"` and no interactive role.

---

### Step 4 Operate every control with the keyboard

**Action:** With focus on each reachable control, activate it using the key expected for its role and confirm the same outcome a mouse click produces. Use this reference for standard patterns:

| Component | Keys |
|---|---|
| Button | Enter or Space to activate |
| Link | Enter to activate |
| Checkbox | Space to toggle |
| Radio group | Arrow keys to move and select within the group |
| Select / listbox | Arrow keys to change option, Enter to confirm |
| Menu / menu bar | Arrow keys to navigate, Enter or Space to activate, Escape to close |
| Tabs | Arrow keys to switch tab, Tab to move into the panel |
| Slider | Arrow keys to adjust, Home and End for min and max |
| Modal dialog | Tab and Shift+Tab within, Escape to close |
| Disclosure / accordion | Enter or Space to expand and collapse |

**Expected result:** Every control produces the same result from the keyboard that it produces from a mouse, with no timing dependency on how fast or slow keys are pressed.

**Fail signal:** A control can be focused but not activated from the keyboard, performs a different or partial action, or requires a precise keystroke speed to register.

---

### Step 5 Verify custom widget keyboard interaction patterns

**Action:** For each custom scripted widget identified in Step 2, compare its keyboard behaviour against the expected design pattern in the ARIA Authoring Practices Guide for that widget type. Confirm the full set of supported keys, not just initial focus. For example, a custom menu should support Arrow keys to move between items, Escape to close, and Enter or Space to activate; a custom combobox should support Arrow keys to move through options and Escape to dismiss the list.

**Expected result:** Each custom widget implements the keyboard interaction expected for its role, so a keyboard user can perform every action a mouse user can.

**Fail signal:** A custom widget is reachable and partly operable but is missing expected keys, for example a menu that opens on Enter but offers no Arrow key navigation, or a slider that focuses but does not respond to Arrow keys.

---

### Step 6 Check hover-only behaviour and drag-and-drop alternatives

**Action:** Identify any functionality that appears only on hover (flyout menus, reveal-on-hover action buttons, tooltips that contain links or controls) and confirm the same content and controls are reachable and operable from the keyboard, typically on focus. Separately, for any drag-and-drop, sortable, or pointer-path interaction, confirm a keyboard alternative completes the same task, for example reorder buttons, a move-to control, or Arrow key repositioning.

**Expected result:** All hover-exposed functionality is also available on keyboard focus, and every drag-and-drop task has a working keyboard alternative.

**Fail signal:** A control or link is exposed only on mouse hover with no focus equivalent, or a task can be completed only by dragging with a pointer.

---

### Step 7 Screen reader verification, including Forms Mode

**Action:** Repeat the operation of each interactive control with a screen reader running, because screen reader users do not always send raw keystrokes straight to the page. Test in at least two combinations from NVDA + Chrome, Edge, or Firefox; JAWS + Chrome, Edge, or Firefox; and VoiceOver + Safari.

The key distinction to verify is the reading mode:

- In **Browse Mode** (NVDA) or the **Virtual PC Cursor** (JAWS), the screen reader intercepts single-character and Arrow keys to read the page, so those keys do not reach a widget's own handlers. This is expected for reading static content.
- In **Focus Mode** (NVDA) or **Forms Mode** (JAWS), keystrokes pass through to the focused control, so a widget's Arrow, Enter, Space, and Escape handlers receive them.

For each custom widget, move to it and confirm the screen reader switches into Focus Mode or Forms Mode automatically when the element has an appropriate interactive role (for example a button, listbox, slider, menu, or combobox role). Then confirm the widget operates with the same keys verified in Steps 4 and 5. If automatic switching does not occur, toggle manually (NVDA: Insert+Space; JAWS: Enter to force Forms Mode, NumPad Plus to return to the Virtual PC Cursor) and re-test. With VoiceOver, use Tab to move between controls and operate them directly, and use the VoiceOver cursor (VO+Arrow) to confirm reading does not block operation.

**Expected result:**

- Native controls operate identically with the screen reader running.
- Custom widgets trigger automatic Focus Mode or Forms Mode because they expose a correct interactive role, and once in that mode every documented key works.
- The user can complete every task with the screen reader active using only the keyboard.

**Fail signal:**

- A widget's Arrow, Enter, or Space keys never reach it because the screen reader stays in Browse Mode or the Virtual PC Cursor, which usually means the element lacks the interactive role that would trigger automatic mode switching.
- A control that worked for a sighted keyboard user cannot be operated by a screen reader user, because mode switching does not occur and manual toggling is the only workaround.

---

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated and visual checks | Zero relevant violations, or all flagged items confirmed false positives in later steps | A clickable element is reported with no keyboard role or interactive semantics and is not resolved |
| 2 Inventory | A complete list of interactive elements is recorded with native or custom classification | Not applicable, discovery step |
| 3 Reach controls | Every interactive control is reachable by keyboard, as a tab stop or as an inner item with expected keys | A pointer-operable control cannot be reached by any keyboard means |
| 4 Operate controls | Every control produces the same outcome from the keyboard as from a mouse, with no timing dependency | A control can be focused but not activated, behaves differently, or needs a precise keystroke speed |
| 5 Custom widget patterns | Each custom widget supports the full keyboard interaction expected for its role | A custom widget is missing expected keys for its widget type |
| 6 Hover and drag alternatives | Hover functionality is available on focus, and every drag task has a keyboard alternative | Functionality is hover-only with no focus equivalent, or a task needs pointer dragging |
| 7 Screen reader and Forms Mode | Custom widgets auto-switch to Focus or Forms Mode and operate with the expected keys in at least two screen reader and browser pairs | A widget never receives its keys because the screen reader stays in Browse Mode or Virtual PC Cursor |

**Overall result:** The page **passes** SC 2.1.1 only when every applicable step passes.
A single step failure = **SC 2.1.1 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **Arrow keys not reaching a widget while a screen reader is in Browse Mode on static content:** Browse Mode and the Virtual PC Cursor intentionally capture reading keys. This is correct behaviour for non-interactive content. It is only a failure when an interactive widget that should trigger Focus Mode or Forms Mode does not.
- **Single tab stop into a composite widget:** A correctly built radio group, tab list, menu, or grid exposes one tab stop and uses Arrow keys for inner navigation. Reaching only one item with Tab is not a failure if the documented Arrow, Home, and End keys reach the rest.
- **Skip links visible only on focus:** A "Skip to main content" link that appears only when focused is a correct pattern, not an unreachable control.
- **Path-dependent essential input:** Freehand drawing or handwriting recognition where the exact path is essential is exempt. Confirm the path is genuinely essential, and check whether an alternative method is offered as good practice.
- **`tabindex="-1"` on a programmatic focus target:** An element given `tabindex="-1"` so script can move focus to it does not create a tab stop and is not an operability failure.

These situations can look like passes but are not:

- **Reachable but only partly operable:** A custom widget that focuses and opens but is missing Arrow key navigation or Escape is a failure, even though it appears to respond to the keyboard.
- **Works for a sighted keyboard user but not with a screen reader:** A widget that responds to keys when no screen reader is running, but never receives them because it lacks the interactive role that triggers Focus or Forms Mode, is not operable for assistive technology users. Record this as a 2.1.1 concern and check SC 4.1.2, since a missing or wrong role is the usual root cause.
- **Operable only after a manual mode toggle:** If a user must manually force Forms Mode for a widget to work because automatic switching never happens, do not record a clean pass. Real users will not know to do this.
- **Hover content that has a focus state but no keyboard activation:** A menu that visually opens on focus but whose items cannot be activated by keyboard still fails.

---

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 2.1.2 No Keyboard Trap (Level A):** A control reachable and operable by keyboard must also allow focus to move away again. Trapping is a separate 2.1.2 failure.
- **SC 2.1.3 Keyboard No Exception (Level AAA):** The same requirement without the path-dependent exception. Reference only as best practice for projects targeting AAA, not as an obligation under AA.
- **SC 2.4.3 Focus Order (Level A):** If a control is reachable but the order is illogical, that is 2.4.3. If it cannot be reached at all, it is 2.1.1.
- **SC 2.4.7 Focus Visible (Level AA):** Keyboard operability is hard to verify if the focus indicator is not visible. Confirm 2.4.7 before recording results here.
- **SC 2.5.7 Dragging Movements (Level AA):** A drag interaction with no keyboard alternative fails 2.1.1, and the lack of a single-pointer alternative separately engages 2.5.7.
- **SC 4.1.2 Name, Role, Value (Level A):** A missing or wrong role is the most common reason a custom widget is unreachable, unoperable, or never triggers Focus or Forms Mode. Keyboard failures and role failures frequently appear together.
