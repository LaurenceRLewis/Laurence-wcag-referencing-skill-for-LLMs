# SC 2.1.4 — Character Key Shortcuts (Level A) — Manual Test Pattern

## 1 — Overview

**SC:** 2.1.4 — Character Key Shortcuts (Level A)
**Intent:** Verify that any keyboard shortcut implemented using only printable character keys (letters, numbers, punctuation, symbols) can be turned off, remapped to include a non-printable modifier key, or is scoped to fire only when a specific component has focus.
**Scope of this test:** Web pages and web applications that implement custom keyboard shortcuts. The SC targets shortcuts operating at document or application level — not standard widget navigation patterns.

---

## 2 — Scope: what to test

Apply these tests to:

- Any page-level or application-level keyboard shortcut that fires regardless of where focus currently sits
- Shortcut sequences composed entirely of printable characters (e.g. pressing `G` then `I` in sequence)
- Any custom shortcut mechanism documented or discoverable by the tester
- Web applications where shortcut keys are a primary navigation or command mechanism (email clients, productivity tools, media players, CMS editors)

Do **not** test:

- Standard widget type-ahead: single-character key presses within a focused `<select>`, `role="listbox"`, `role="menu"`, `role="menubar"`, `role="tree"`, `role="grid"`, or `role="combobox"` popup. These fire only while the widget has focus and are explicitly exempt by the SC's third passing condition and confirmed by W3C Failure Technique F99.
- Arrow key navigation inside composite ARIA widgets — arrow keys are not printable characters and are out of scope entirely.
- Any shortcut requiring a non-printable modifier key as part of its activation (e.g. `Ctrl+S`, `Alt+F`, `Cmd+C`). Modifier-dependent shortcuts are categorically exempt.
- The `accesskey` HTML attribute. Browser implementations universally require a modifier key combination (e.g. `Alt+Shift+[key]`) to invoke `accesskey` values, so they do not meet the SC's definition of a character key shortcut. Note: `accesskey` carries separate usability concerns but is not a SC 2.1.4 issue.
- Static content with no interactive behaviour.
- Native browser shortcuts (e.g. `Ctrl+F` for find). The SC applies to shortcuts **implemented in content**, not the browser itself.

---

## 3 — Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Chrome, Edge, or Firefox) | Inspect event listeners on `document` and `window` to identify script-based shortcut handlers | Yes |
| A11y Quick Check browser extension | No dedicated check for SC 2.1.4 — no automated detection is possible for script-based shortcuts | Yes |
| axe DevTools browser extension | Automated scan — limited coverage; axe can flag some global shortcut patterns but cannot fully detect listener-based shortcuts | Yes (core) |
| Page documentation / keyboard shortcut help | Many web apps publish a shortcut reference (e.g. `?` key, `Help` menu, or a documented shortcut list) — use this to identify shortcuts before testing | — |

> **Note:** There is no automated tool that reliably detects all character key shortcuts because they are typically implemented via JavaScript event listeners (`document.addEventListener('keydown', ...)`) which cannot be enumerated by injected scripts or browser extensions. This test is inherently manual.

---

## 4 — Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 — Discover whether the page implements character key shortcuts

**Action:** Check for a keyboard shortcut reference by: pressing `?` (a common help trigger in web apps); looking for a Help menu or settings panel listing shortcuts; reading any published documentation for the page or app. Then open DevTools → Elements panel → Event Listeners tab, select `document` in the DOM tree, and look for `keydown`, `keyup`, or `keypress` listeners. Expand any found listeners to inspect their source.

**Expected result:** If no shortcuts are implemented, the test is N/A. If shortcuts are present, they are documented or discoverable, and the tester has a list of which character keys trigger actions.

**Fail signal:** Not applicable at this step — this step is discovery only.

---

### Step 2 — Identify which shortcuts use only printable character keys

**Action:** From the shortcut list discovered in Step 1, classify each shortcut. A shortcut is in scope if its trigger is: a letter (upper or lower case), a number, a punctuation mark, or a symbol character — even if a physical modifier key (like `Shift`) is needed to produce that character on a given keyboard layout. A shortcut is out of scope if it requires `Ctrl`, `Alt`, `Meta`/`Cmd`, or `Fn` as an explicit, named part of the shortcut.

**Expected result:** The tester has a confirmed list of in-scope character key shortcuts to test in subsequent steps.

**Fail signal:** Not applicable at this step — this step is classification only.

---

### Step 3 — Test whether shortcuts fire globally (outside component focus)

**Action:** Place focus in a plain text area or input field on the page (or, if none exists, click an empty area of the page body). Then press each in-scope character key shortcut identified in Step 2.

**Expected result:** A conformant page either: (a) does not trigger the shortcut while focus is in a text input — the key simply types the character as expected; or (b) triggers the shortcut but immediately provides a mechanism to turn it off or remap it (tested in Step 4).

**Fail signal:** The shortcut fires while focus is inside a text field, overriding normal text input — and there is no mechanism to disable or remap it. This is a clear global shortcut with no scope limiting.

---

### Step 4 — Verify a turn-off or remap mechanism exists

**Action:** Look for a settings, preferences, or keyboard shortcut customisation panel within the page or application. Check whether it provides: (a) a toggle to disable individual shortcuts or all character key shortcuts; or (b) a remapping control that allows the shortcut to be changed to one that includes a non-printable modifier key (`Ctrl`, `Alt`, `Meta`/`Cmd`).

**Expected result:** At least one of the following is true for every in-scope shortcut identified in Step 2:
- A mechanism exists to turn the shortcut off.
- A mechanism exists to remap it to a modifier-key combination.
- The shortcut is only active when a specific, narrowly defined component has focus (not the page body or a broad wrapper).

**Fail signal:** No such mechanism exists. Shortcuts fire globally and cannot be disabled or remapped.

---

### Step 5 — Verify the mechanism itself is accessible

**Action:** If a turn-off or remap mechanism was found in Step 4, test it using keyboard only. Navigate to the settings panel using `Tab`/`Shift+Tab`, operate the toggle or remap control, confirm the shortcut is disabled or remapped, and then re-test the shortcut from Step 3.

**Expected result:** The mechanism is keyboard operable. After disabling or remapping, pressing the original shortcut key no longer triggers the action (or triggers the newly mapped action instead).

**Fail signal:** The settings mechanism is mouse-only or otherwise inaccessible by keyboard. Or the disable/remap action does not take effect — the original shortcut still fires.

---

### Step 6 — Test character key sequences

**Action:** If any shortcuts from Step 2 use a sequence of character keys (e.g. `G` then `I`, `G` then `A`), test these individually following the same process as Steps 3–5. Sequences of only printable characters are in scope regardless of how many keys are pressed.

**Expected result:** Same passing conditions as Step 4 apply — each sequence can be turned off, remapped, or is focus-scoped.

**Fail signal:** A character key sequence fires globally and has no mechanism to disable or remap it.

---

## 5 — Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 | No shortcuts exist (N/A), or a shortcut reference is discoverable | Not applicable — discovery step |
| 2 | Each shortcut is correctly classified as in scope or out of scope | Not applicable — classification step |
| 3 | In-scope shortcuts do not fire while focus is in a text field; or they fire but a mechanism to disable/remap exists | A shortcut fires globally, including inside text inputs, with no disable/remap mechanism |
| 4 | A turn-off or remap mechanism exists for every in-scope shortcut | No mechanism exists for one or more in-scope shortcuts |
| 5 | The mechanism is keyboard accessible and effective | The mechanism is inaccessible by keyboard, or disabling/remapping has no effect |
| 6 | Character key sequences meet the same conditions as single-key shortcuts | A sequence fires globally with no mechanism to disable or remap it |

**Overall result:** The page **passes** this SC only when every applicable step passes. A single step failure = **SC failure**.

---

## 6 — Common false positives

These situations can look like failures but are not:

- **ARIA widget type-ahead (listbox, menu, tree, grid, combobox popup):** Pressing a letter key while one of these widgets has focus to jump to a matching option is not a character key shortcut in scope of SC 2.1.4. The shortcut is active only when that specific component has focus — this is the SC's third passing condition, satisfied by design. Do not flag these.
- **`accesskey` attributes:** The `accesskey` attribute requires a browser-specific modifier key combination to invoke (e.g. `Alt+Shift+[key]` on Windows in Firefox). This means `accesskey` shortcuts are not character-key-only shortcuts and are exempt from SC 2.1.4. They carry separate usability and discoverability issues but do not fail this SC.
- **Modifier-required shortcuts displayed as character keys in UI labels:** Some interfaces label shortcuts as single characters in their UI (e.g. showing `S` for save) but actually require `Ctrl+S` to trigger. Confirm the actual trigger before scoring.
- **Native `<select>` elements:** Type-ahead in a native `<select>` is browser-implemented behaviour, not author-implemented content. It is out of scope.

These situations can look like passes but are not:

- **A settings panel that is mouse-only:** If a remap or disable mechanism exists but is itself not keyboard accessible, it does not satisfy the SC. The mechanism must meet all applicable success criteria for the conformance level claimed.
- **A shortcut scoped to `document.body` or a broad wrapper:** The SC requires focus to be on the specific component the shortcut relates to. A shortcut that fires whenever focus is anywhere on the page body is a global shortcut, not a focus-scoped one.
- **Shortcuts that appear disabled but still fire:** Confirm after using the disable mechanism that the shortcut actually no longer triggers its action.

---

## 7 — Related criteria

Failures here often co-occur with failures in:

- **SC 2.1.1 — Keyboard (Level A):** If a page relies heavily on character key shortcuts for functionality, missing keyboard support elsewhere may also be present.
- **SC 2.1.2 — No Keyboard Trap (Level A):** Applications with complex shortcut systems sometimes create focus management problems alongside shortcut issues.
- **SC 4.1.2 — Name, Role, Value (Level A):** Custom shortcut controls in settings panels may lack proper accessible name or role markup, compounding the accessibility failure.
