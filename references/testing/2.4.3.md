# SC 2.4.3 Focus Order (Level A) — Manual Test Pattern

## 1 Overview

**SC:** 2.4.3 Focus Order (Level A)
**Intent:** Verify that focusable components receive focus in an order that preserves meaning and operability, so keyboard and assistive technology users encounter content in a sequence consistent with its visual and logical structure.
**Scope of this test:** All focusable elements on the page, including interactive controls, dynamic content, and modal dialogs.

---

## 2 Scope: what to test

Apply these tests to:

- All natively focusable elements: links, buttons, form inputs, selects, textareas
- Custom interactive components using `tabindex="0"`
- Modal dialogs and other overlay patterns
- Dynamically inserted content: expanded panels, inline error messages, notifications, step-by-step flows
- Single-page application (SPA) route changes where new content is loaded without a full page reload

Do **not** test:

- Elements with `tabindex="-1"` that are intentionally removed from the tab order (unless they should be reachable)
- Decorative or non-interactive content with no focusable descendants
- Focus indicator visibility or appearance (covered by SC 2.4.7 and SC 2.4.11)
- Whether all functionality is keyboard operable (covered by SC 2.1.1)

---

## 3 Tools required

| Tool | Purpose | Free? |
|------|---------|-------|
| Browser DevTools (Chrome, Edge, or Firefox — Elements panel) | Inspect `tabindex` values, DOM order, and focus management attributes | Yes |
| A11y Quick Check browser extension | Run "Validate Tabindex usage" and "Focus Order" checks from the "Usability and Readability" tab | Yes |
| axe DevTools browser extension (or your preferred automation testing tool) | Automated scan to surface positive `tabindex` values and focus order violations | Yes (core) |
| Keyboard only (Tab, Shift+Tab, Arrow keys, Enter, Space, Escape) | Manually walk the tab sequence to observe focus order in practice | N/A |
| NVDA + Chrome, Edge, or Firefox (Windows) | Verify focus order and dynamic focus movement as announced by a screen reader | Yes |
| JAWS + Chrome, Edge, or Firefox (Windows) | Verify focus order with a commercial screen reader on Windows | No |
| VoiceOver + Safari (macOS / iOS) | Verify focus order on Apple platforms | Yes (built-in) |

> **Configuration note:** Disable mouse use entirely during keyboard testing to avoid accidentally repositioning focus. In Chrome and Edge, the Tab key moves focus between interactive elements; in Firefox, `about:config` → `accessibility.tabfocus` may need to be set to `7` to enable full tab focus on all interactive elements. Before screen reader testing, set NVDA to Browse Mode (Insert+Space to toggle); use Tab for interactive elements and arrow keys for reading order.

---

## 4 Test steps

Work through every step in sequence. Record a result (Pass / Fail / N/A) for each step.

### Step 1 Run automated and visual checks

**Action:** Activate A11y Quick Check and run "Validate Tabindex usage" and "Focus Order" from the "Usability and Readability" tab. Review the overlay, which numbers focusable elements in DOM sequence and flags positive `tabindex` values. Then activate axe DevTools browser extension (or your preferred automation testing tool) and run a full-page scan. Note any violations related to: `tabindex`, `focus-order-semantics`, or similar focus and tab order rules.

**Expected result:** Zero violations in focus order categories, or each flagged item is confirmed as a false positive in Step 2.

**Fail signal:** Any unresolved violation involving positive `tabindex` values or focus order semantics.

---

### Step 2 Audit `tabindex` values in the DOM

**Action:** Using the A11y Quick Check overlay from Step 1 as a starting point, open DevTools and in the Console run: `document.querySelectorAll('[tabindex]')` to list all elements with a `tabindex` attribute. For each result, note whether the value is negative (`-1`), zero (`0`), or positive (`1` or higher).

**Expected result:**
- No element has a `tabindex` value greater than `0`.
- Elements with `tabindex="0"` are custom interactive components that legitimately need to be in the tab order.
- Elements with `tabindex="-1"` are either managed programmatically (focus sent to them via JavaScript) or intentionally removed from the tab sequence.

**Fail signal:**
- One or more elements have `tabindex="1"` or higher, overriding the natural DOM tab order.
- A large number of elements have `tabindex="0"` applied unnecessarily to non-interactive elements such as `<div>` or `<span>` containers.

---

### Step 3 Walk the tab sequence on the page at rest

**Action:** Place focus at the top of the page (click the browser address bar, then press Tab once to enter the page). Tab through every focusable element in sequence without activating any. As you Tab, note the visual order in which elements receive focus.

**Expected result:**
- Focus moves top to bottom, left to right (in a left-to-right language), following the logical reading sequence of the page.
- Focus does not jump backwards, skip large sections unexpectedly, or move to a visually unrelated part of the page.
- The tab sequence matches the visual layout: elements that appear earlier on screen receive focus earlier.

**Fail signal:**
- Focus jumps from a navigation link to a footer element, skipping the main content area.
- A form field in the middle of the page receives focus before fields that appear above it visually.
- Focus returns to the top of the page or to a previously visited element without user action.

---

### Step 4 Check focus management on dynamic content

**Action:** Identify all interactions that insert, reveal, or update content dynamically: accordion panels, tab interfaces, modal dialogs, inline error messages, toast notifications, and step-by-step flows. For each, perform the triggering action (click or keyboard activate the control) and observe where focus moves.

For each dynamic pattern, verify:

| Pattern | Expected focus destination |
|---|---|
| Modal dialog opens | First focusable element inside the dialog, or the dialog container itself if no focusable child exists |
| Modal dialog closes | The element that triggered the dialog |
| Accordion panel expands | Focus remains on the trigger (panel content is revealed but focus does not move) |
| Inline error appears | Focus moves to the error message or the invalid field, depending on implementation |
| SPA route change | Focus moves to the new page heading or a skip target at the top of the new view |
| Step / wizard advances | Focus moves to the heading or first meaningful element of the new step |

**Expected result:** For each pattern, focus lands on a logical, predictable destination that allows the user to immediately interact with or read the newly available content.

**Fail signal:**
- A modal dialog opens but focus remains behind it on the triggering element or an unrelated part of the page.
- A modal closes and focus is lost (moves to `<body>` or the top of the document) rather than returning to the trigger.
- An inline error message appears but focus stays on an unrelated field, requiring the user to navigate back to find the error.
- An SPA route change reloads content but focus remains at the bottom of the previous view.

---

### Step 5 Verify focus is not trapped outside intentional modal patterns

**Action:** Tab through the entire page, including any custom widgets. Confirm that focus never becomes stuck in a loop from which there is no keyboard exit, except inside an intentionally modal dialog where trapping is correct behaviour. For any component that does trap focus (a dialog, a drawer, a lightbox), confirm that pressing Escape or activating a visible close control returns focus to the trigger and releases the trap.

**Expected result:**
- Focus moves freely through all page regions without getting stuck.
- Intentional focus traps (modals) release correctly on Escape or close action and return focus to the trigger.

**Fail signal:**
- Tabbing into a custom widget cycles focus indefinitely within it with no way to exit.
- A modal dialog closes but focus is not returned to the trigger element.
- Escape does not close a modal or release a focus trap.

---

### Step 6 Verify reading order matches DOM order for meaningful content

**Action:** Open DevTools and disable all CSS (in Chrome or Edge: open the Command Menu with `Ctrl+Shift+P`, search "Disable CSS"; in Firefox: View menu → Page Style → No Style). Review the page in its unstyled state. Confirm that the order of content in the DOM matches the intended logical reading order.

**Expected result:** When CSS is removed, the content sequence still makes sense. Headings precede the content they introduce; form labels appear before or adjacent to their inputs; navigation landmarks appear in a logical position relative to main content.

**Fail signal:**
- With CSS disabled, content appears in a sequence that does not reflect logical reading order: a sidebar renders before the main content it is visually positioned beside; a form submit button appears in the DOM before the fields it submits.

---

### Step 7 Screen reader verification of focus sequence

**Action:** Using NVDA + Chrome, Edge, or Firefox (and separately with JAWS + Chrome, Edge, or Firefox or VoiceOver + Safari), Tab through the page and through any dynamic content patterns identified in Step 4. Listen to the sequence of announcements and confirm they match the expected logical order.

**Expected result:**
- The screen reader announces elements in a sequence that reflects the page's logical structure.
- When a modal opens, the screen reader immediately announces content within the dialog.
- When a modal closes, the screen reader announces the trigger element that re-received focus.
- Dynamic content insertions are announced at the correct point in the reading sequence.

**Fail signal:**
- The screen reader announces elements in an order that does not match the visual or logical structure of the page.
- After a modal opens, the screen reader continues announcing content from behind the dialog.
- After a modal closes, the screen reader announces an unexpected element rather than the trigger.

## 5 Pass / Fail criteria

| Step | Passes when | Fails when |
|------|-------------|------------|
| 1 Automated and visual checks | Zero relevant violations, or all flagged items confirmed false positives | Any unresolved positive `tabindex` or focus order violation |
| 2 `tabindex` audit | No `tabindex` values greater than `0` in the DOM | Any element has `tabindex="1"` or higher |
| 3 Tab sequence at rest | Focus moves in logical top-to-bottom, left-to-right order matching visual layout | Focus jumps unpredictably, reverses, or skips significant page regions |
| 4 Dynamic content focus | Focus moves to a logical destination when content is inserted or revealed; returns to trigger on close | Focus lost, stranded behind a modal, or left on an unrelated element after a dynamic change |
| 5 Focus trap check | Focus moves freely; intentional traps release correctly on Escape or close | Focus stuck in a loop with no keyboard exit; modal closes without returning focus to trigger |
| 6 DOM order | Logical reading order preserved when CSS is removed | Content sequence without CSS does not match intended reading order |
| 7 Screen reader | Announcements follow logical sequence; dynamic focus changes announced correctly | Screen reader announces out-of-order content; modal or dynamic content not announced at the correct point |

**Overall result:** The page **passes** SC 2.4.3 only when every applicable step passes.
A single step failure = **SC 2.4.3 failure**.

---

## 6 Common false positives

These situations can look like failures but are not:

- **Accordion panels that do not move focus on expand:** When an accordion trigger expands a panel, focus correctly stays on the trigger. The revealed content is navigable by continuing to Tab. This is not a focus order failure.
- **Skip links that appear only on focus:** A "Skip to main content" link that is visually hidden until focused is a legitimate and correct pattern. Its position at the top of the tab order is intentional.
- **CSS-only reordering that preserves DOM order:** If `flex-order` or `grid` visually repositions elements but the DOM order remains logical, and the DOM order matches the intended reading sequence, this passes SC 2.4.3. It may still be a maintenance concern, but it is not a failure of this SC.
- **`tabindex="-1"` on focusable elements used as programmatic focus targets:** A heading or container with `tabindex="-1"` that receives focus programmatically (for example, after an SPA route change) is correct behaviour. It does not create a tab stop and does not disrupt the tab sequence.

These situations can look like passes but are not:

- **Visual tab order that looks correct but relies on positive `tabindex`:** If the tab sequence matches the visual order only because of carefully managed positive `tabindex` values, the implementation is fragile and any future DOM change can break it. This is a failure of Step 2 regardless of whether the current tab sequence appears correct.
- **Focus returned to the correct region but not the correct element:** After a modal closes, focus should return to the specific trigger element, not just somewhere near it. Focus landing on a parent container or adjacent element is a failure.
- **Dynamic content that receives focus in the correct position only in one screen reader:** A focus management pattern that works in NVDA but not in JAWS, or vice versa, is not a reliable pass. Test in at least two screen reader and browser combinations before recording a pass.

---

## 7 Related criteria

Failures here often co-occur with failures in:

- **SC 2.1.1 Keyboard (Level A):** If focus order is broken because a component is not reachable by keyboard at all, that is a 2.1.1 failure. SC 2.4.3 applies when the component is reachable but the order is illogical.
- **SC 2.1.2 No Keyboard Trap (Level A):** A focus trap that does not release (Step 5) is simultaneously a 2.1.2 failure.
- **SC 1.3.2 Meaningful Sequence (Level A):** Requires that the reading order implied by the content sequence is correct. DOM order failures identified in Step 6 often fail both 1.3.2 and 2.4.3.
- **SC 2.4.7 Focus Visible (Level AA):** Focus order cannot be verified manually if the focus indicator is not visible. Always confirm SC 2.4.7 before recording results for this SC.
- **SC 2.4.11 Focus Not Obscured Minimum (Level AA):** A focused element obscured by a sticky header or overlay may appear to disrupt focus order when the real issue is visibility. Check 2.4.11 before attributing a jump to a focus order failure.
- **SC 4.1.3 Status Messages (Level AA):** Dynamic content that inserts status messages (errors, confirmations) may fail 2.4.3 if focus is not managed correctly, and separately fail 4.1.3 if the message is not announced via a live region.
