# SC 2.1.1 — Keyboard (Level A)

## Intent
All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes — so users who cannot use a mouse can access all features.

## Passes when
- Every interactive element can be reached and activated with keyboard alone (Tab, Shift+Tab, Enter, Space, Arrow keys)
- Custom widgets implement correct keyboard interaction patterns per the ARIA Authoring Practices Guide
- Drag-and-drop interactions have a keyboard alternative (see SC 2.5.7)

## Fails when
- Mouse-only event handlers (`onmousedown`, `onmouseover`, `onclick` without keyboard equivalent) used on custom elements
- Custom `<div>` or `<span>` used as an interactive control without keyboard support
- A feature is only accessible via hover with no keyboard equivalent
- Drag-and-drop is the only way to complete a task

## Exception
Functionality that requires a path-dependent input where the path itself is essential — freehand drawing, handwriting recognition — is exempt. An alternative method should be provided where possible.

## Common keyboard patterns

| Component | Keys |
|---|---|
| Button | Enter or Space to activate |
| Link | Enter to activate |
| Checkbox | Space to toggle |
| Radio group | Arrow keys to move between options |
| Modal | Escape to close; Tab/Shift+Tab within |
| Menu | Arrow keys to navigate; Escape to close |
| Tabs | Arrow keys to switch tabs |
| Slider | Arrow keys to adjust value |

No change from WCAG 2.1.
